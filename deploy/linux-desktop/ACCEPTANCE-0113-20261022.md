## Owner-only live upgrade

The test instance upgraded from `0.1.108-cloud.2` to `0.1.113-cloud.1`; its main
container and init use the same pinned candidate digest. The existing CIS
maintenance flow seals writes, stops the source, creates a read-only encrypted OSS
backup, starts the candidate, verifies it and releases maintenance. The backup
contains 3,211 files, 1,121,658,368 tar bytes and 436,634,438 encrypted bytes;
backup execution took 27,765 ms. The operation completed and the runtime is
released, Ready and at zero container restarts.

Sealed before/after checks preserve selected business table counts and full-row
schedule hashes, pass SQLite integrity checks and show no new crash dumps. Runtime
identity, persistent-volume identity, resource allocation and update preferences
are preserved. All other 11 instance records, StatefulSet specifications and Pod
identities are unchanged; the stopped instance remains stopped. New-claim defaults
are unchanged. The shared CIS maintenance implementation is unchanged; only the
owner's exact candidate admission was added through configuration.

The first operator attempt observed a transient unknown activity sample and
skipped before creating a maintenance operation or stopping the instance. Fresh
observations subsequently showed known-idle activity and a separate retry completed
the normal protected flow. No unknown count was overwritten or treated as idle.
